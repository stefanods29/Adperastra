This is a complete implementation guide, not implementation code. Coding workers write owned code and tests without installing, compiling, running tests, starting prototypes or building the app. The coordinator performs shared wiring, executed verification and integration. Consumers 20b, 21a, 22a and the complete 22b can be written concurrently against this contract. A real engine binding remains gated by the explicit checkpoint; an unavailable engine never returns fake success.

## Goal and exclusions

Provide one engine-neutral editing boundary for documents, workbooks and presentations, compare feasible local engines against retained corpus evidence, and integrate only the owner-approved implementation. No cloud document service, AI writing, AI formulas, dictation, model pack, macro execution, paid Office I/O, or invented engine API. Existing accurate viewing and opening in the chosen app remain available. 20c and 21b are not prerequisites for these ordinary editors.

## Decisions

- D1. Separate the stable application contract from a selected engine's API. The five modules `src/office/{types,documentOperations,sheetOperations,deckOperations,adapter}.ts` define the public TypeScript boundary; mirrors live in `src-tauri/src/office_edit_{types,document,sheet,deck}.rs`. Each stays below 400 lines; shared value types belong in `officeValues.ts` and `office_edit_values.rs`. The `office-edit-1` fields and names below are authoritative.
- D2. Compare Collabora desktop technology, ZetaOffice/ZetaJS and native LibreOfficeKit for supported Windows integration. The fallback order is accurate read-only view/conversion, an explicitly approved basic editor with permissive open-source components and our own proven Office I/O, then the chosen external app. A product name does not prove Windows availability, embeddability, license suitability or free import/export. ONLYOFFICE, AGPL components and paid Univer import/export are excluded.
- D3. **OWNER CHECKPOINT after T4.** The coordinator executes the spikes and presents one measured recommendation per family. The owner chooses a documented engine/fallback. Record exact version, source commit, artifact hash, licenses/notices, source availability and replaceable LGPL boundaries before the binding task. Until then `approved_engine` is absent; editing capabilities are false, and open returns `office_edit.engine_missing`. This checkpoint does not block authoring or coding unrelated UI against the frozen adapter.
- D4. One approved warm Office engine pool serves all editor tabs; maximum four live edit sessions and one active mutation per session. A separate helper process hosts risky parsing and calculation, with a 2 GiB aggregate job memory ceiling, 512 MiB input, 1 GiB expanded package, 100,000 package entries, ratio 500 and depth 64. Queue at most 32 requests, DTO at most 768 KiB, raw chunks at most 8 MiB through authorized protocol streams. Open timeout 60 s; ordinary transaction 10 s; export 120 s; cancel kills an unresponsive helper within 250 ms. Idle warm engine expires after 5 minutes with no sessions; dirty content is not evicted without recovery or a user decision.
- D5. Native engine state is authoritative for content and permissions. The UI never supplies an output path to engine dispatch. Engine reads immutable authorized input and returns an immutable encoded snapshot; the coordinator's document save path performs versioning and identity-bound publication. Source modifications are never a side effect of load, navigation, render, print preview or capability inquiry.
- D6. The source-aware `DocumentRegistry` owns one editing controller per document. Office views acquire references to that controller; they do not load independent writable copies. Each successful content transaction creates one content identity and one Undo entry; failed or cancelled transactions leave content, selection and history unchanged. Undo/Redo restore content identities while the public revision increases monotonically. Saving captured revision R marks its captured content identity saved; newer edits remain dirty.
- D7. OOXML and ODF preservation is mandatory, not best effort. Retain untouched parts, relationship IDs, namespaces, custom XML, embedded objects and unsupported feature records through a round trip, or disable existing-file save before editing begins. Never silently reconstruct a document using a simplified exporter. The compatibility report distinguishes editable, preserved-only, unsupported and blocked content. Macros, external links, DDE, OLE activation, external data refresh and remote fonts/media never execute. Macro-bearing input remains view-only unless a separately proved preservation-only route is approved; no advertised macro support.
- D8. Native capability decisions combine approved engine, current format/features, protection, edit mode, permissions, source identity and successful fidelity evidence. Unknown capabilities are false. Display disabled controls with `office.unsupported` or `office.enableEditing`, rather than enabled buttons that do nothing. A fallback is an honest limited mode; the full step is not accepted if required fidelity/performance remains unmet.
- D9. Ordinary snapshots use 08a owned storage; sensitive locked-folder inputs and recovery remain memory-only or inside the provider's encrypted store. A backend lacking memory-only input/output refuses sensitive editing with `office_edit.sensitive_unsupported`. The UI cannot downgrade this classification. No plaintext engine profile, swap, autosave, log, clipboard history or render cache may contain sensitive document content.
- D10. Settings schema 49 becomes 50 with `office_edit.enabled` false until engine approval and explicit enabling, `office_edit.autosave_default` false, and `office_edit.idle_minutes` fixed 5. Local session state contains only bounded view/selection information; no document text, tokens, password, snapshot ID or engine process handle. No new runtime library is selected by this guide; approval later supplies an additive dependency record.

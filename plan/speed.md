# Speed

## The standard

The goal is simple: the user should never wait long enough to feel bored or annoyed. We use two well-known standards instead of inventing our own numbers:

- **Nielsen's response-time limits (0.1 s, 1 s, 10 s):** about 0.1 s feels instant; about 1 s keeps the user's flow of thought (they notice the delay but stay focused); about 10 s is the limit of attention, after which people need progress feedback or they switch to something else.
- **Google's RAIL model:** acknowledge input in 100 ms or less, render each animation frame in under 16 ms (60 frames per second), do background work on the UI thread in chunks under 50 ms, and deliver interactive content quickly. (RAIL allows 5 s for loading web pages; a desktop app should do much better, so we use the 1 s limit for opening things.)

## Speed tiers

Every interaction belongs to one tier. Measure them, and fix anything that falls into a slower tier than it should.

| Tier | Limit | What belongs here | What the user must see |
|---|---|---|---|
| **Instant** | 0.1 s | Any click or key press being acknowledged; selection; menus (including the right-click menu); tab switching; typing; hover effects; command palette opening and results; search results updating while typing; toasts; dragging feedback | The result itself |
| **Smooth** | 16 ms per frame | Scrolling, dragging, resizing panels, animations, zooming, brush strokes, video scrubbing (30 fps minimum for video) | No stutter or dropped frames |
| **Fast** | 1 s | App start to a usable Explorer; opening a folder (first rows visible); opening any file (first view visible); quick preview; thumbnails appearing; an editor becoming usable after the view; switching layouts or themes; opening a saved group (first tab) | A skeleton within 0.1 s, then the content |
| **Waiting with feedback** | 1-10 s | Opening very large files fully; the Office editor starting cold; an AI model loading or starting its answer; unlocking a locked folder; converting a single small file; OCR of a large page | A skeleton within 0.1 s; after 1 s, words saying what's happening and progress when known; Cancel available |
| **Background job** | over 10 s | Copying or moving many files; batch conversions; storage scans; duplicate searches; indexing; pack downloads; AI batch actions; video export | Runs in the job queue with percentage, time remaining, and Cancel; I can keep working; a notification when it's done |

Background work must never push foreground interactions out of their tier (RAIL "idle" rule: UI-thread work in chunks under 50 ms; heavy work in Rust threads or helper processes at low priority).

## Where speed is measured

- Measure on the development PC this is being built on. Record its specs in `docs/benchmarks/MACHINE.md`.
- Keep a test corpus in `test-files/` (generated by scripts where possible, so large files aren't committed): text (1 KB to a 2 GB log, generated), images (small JPG to a 100 MP PNG), PDFs (1, 100, and 1,000 pages, plus a scanned one), audio and video (MP3, 1080p, 4K), an archive with 10,000 entries, Office files (10-page and 100-page documents, a 100,000-row sheet, a 50-slide deck), and a generated folder with 100,000 items. Ask me for real files I'd rather use.
- A benchmark script records time-to-first-view and time-to-ready for the corpus and the main interactions, and saves the results as a small JSON file per run in `docs/benchmarks/`, committed with the step. This way speed can be compared across the Git history. A slowdown of more than 20% compared to the previous step fails the test suite.
- Each step report includes a table: interaction, tier, measured time, pass or fail.

## How to stay fast

1. **View first, edit later:** every handler shows a fast preview, then upgrades to its editor in the background ("view now, edit when ready").
2. **Never read a whole file to show the first screen:** stream, read ranges, memory-map, and virtualize. Build indexes (line offsets, page maps) in the background.
3. **Prefetch on intent:** when a file is selected or hovered for about 150 ms, read its head, load its handler's code, and wake its engine. Cancel if the selection moves on.
4. **Keep engines warm:** PDF, media, Office, and AI engines stay alive after first use, with a configurable idle timeout and memory limits.
5. **Cache what's expensive:** thumbnails, first-page renders, parsed metadata, OCR text, and decoded previews, keyed by path + size + modified time + handler version, with a size limit (oldest removed first). Show the cached result instantly and check freshness in the background.
6. **Keep the UI thread free:** decode, parse, and render in Rust threads, helper processes, or Web Workers. Move big data through custom protocols or shared memory, not JSON.
7. **Render progressively:** low resolution first, full resolution after; skeletons as described in `rules.md`.
8. **Cancel and prioritize:** the visible tab loads first; leaving a tab or opening another file cancels obsolete work; opening ten files at once must not freeze anything.
9. **Split code per handler** (lazy loading), preload the most-used parts when idle after startup, and keep the startup bundle small.
10. **Large-file modes:** above a size threshold, text opens read-only and streamed; huge images decode with shrink-on-load or tiles; big sheets virtualize.
11. **Our ribbons render instantly:** controls start disabled and enable as the engine reports ready. Typing is enabled as soon as the document model is loaded, while layout continues in the background.
